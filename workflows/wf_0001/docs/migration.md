It adds no claim about behaviour that those artifacts do not support, and it quotes no number about data: every count, diff and verdict lives in `validation*.json`, written by `scripts/validate_build.py`.

## Purpose

Totals each region's net order value by size band for the weekly sales review, leaving the WEST region out, and lists the orders it left out.

## Source mappings

| Alteryx touchpoint | Logical name | Snowflake | Write mode | Confirmed by |
|---|---|---|---|---|
| `C:\data\sales\orders.yxdb` (tool 1) | `ORDERS` | `SALES.RAW.ORDERS` | read | owner |
| `C:\data\out\sales_summary.yxdb` (tool 7) | `SALES_SUMMARY` | `ANALYTICS.CURATED.SALES_SUMMARY` | overwrite | owner |
| `C:\data\out\excluded_orders.csv` (tool 8) | `EXCLUDED_ORDERS` | `ANALYTICS.CURATED.EXCLUDED_ORDERS` | overwrite | owner |

The build file never names any of these tables: a source is read as `{{src}}.<LOGICAL>` and a target written as `{{tgt}}.<LOGICAL>`, and `src` and `tgt` are filled in when it runs. In validation `src` is the golden view schema `MIG_GOLDEN_WF0001_<SET>` and `tgt` is `MIG_WORK`; in production `src` is the view schema `scripts/gen_source_views.py` generates, `MIG_SRC_WF0001`, which maps the same logical names to the tables above.

## Steps

The diagram of these steps against the lines of `build.sql`, and the table of every Alteryx tool with its step and lines, are generated by `scripts/render_mapping.py` into [`docs/mapping.md`](mapping.md); this record does not repeat them.

- **s1 · Read and clean orders** (tools 1, 2): Reads the ORDERS extract, cuts CUSTOMER to its first 10 characters and renames STATUS to ORDER_STATUS.
- **s2 · Set the WEST region aside** (tools 3): Splits the orders on REGION != "WEST": the True side carries on to the summary; the False side (WEST orders, and orders with no REGION) goes to the excluded list.
- **s3 · Work out net value and size band** (tools 4): Converts AMOUNT_TXT to a number (AMOUNT), applies a 10% discount on quantities of 10 or more and rounds to the cent (NET), and bands each order LARGE, MEDIUM or SMALL by AMOUNT (SIZE_BAND).
- **s4 · Total by region and size band** (tools 5, 6, 7): Sums NET, counts orders and priced orders and takes the latest order date for each region and size band, sorts the biggest totals first and writes SALES_SUMMARY.
- **s5 · List the excluded orders** (tools 8): Writes the orders that were set aside, with their cleaned columns, to EXCLUDED_ORDERS.

## Assumptions

Every assumption is listed one per line in `translation_notes.md`; no lint flag is raised, so none is kept. The ones a reader of this document should know about:

- Tools 1 and 2 are read once into the temporary table `clean_orders`, because both outputs start from the same cleaned rows; each output is then written once with `CREATE OR REPLACE TABLE`, its write mode being overwrite.
- Tool 2's `String(10)` retype of `CUSTOMER` is `LEFT(CUSTOMER, 10)`: Alteryx truncates silently where a Snowflake `VARCHAR(10)` would raise, and `LEFT` counts characters, so the non-ASCII customer in the `edge` set truncates by character and not by byte.
- Tool 2's `*Unknown` selection appends the five unlisted fields in incoming order, which fixes the column order of `EXCLUDED_ORDERS` as `CUSTOMER, ORDER_STATUS, ORDER_ID, REGION, AMOUNT_TXT, QTY, ORDER_DATE`.
- Tool 3's Filter sends a NULL `REGION` to the False anchor: `SALES_SUMMARY` reads `WHERE REGION <> 'WEST'`, where a NULL is not true, and `EXCLUDED_ORDERS` reads `WHERE NOT (REGION <> 'WEST') OR REGION IS NULL`, so the NULL-region order reaches it.
- `ToNumber` is translated as `TRY_TO_DOUBLE`; on the local runtime it accepts `inf` and `nan` where the model would give NULL, and no golden set contains either, so that divergence is recorded rather than guarded against.
- `CAST(<double> AS NUMBER(38,10))` is assumed to reproduce the model's decimal conversion of a stored `Double`. It does for every amount in the golden sets, each of which has at most three decimal places; a value needing more than ten would round here and not there.
- The local runtime gives `NUMBER(38,10) * NUMBER(38,10)` scale 20; Snowflake documents scale `min(S1 + S2, max(S1, S2, 12))` for multiplication, so the product carries scale 12 there. That is enough for this workflow's arithmetic and needs verification on Snowflake.
- `TOTAL_NET` adds the exact `NUMBER` values of `NET` and casts the total to `FLOAT` once, as the model adds exact decimals and stores once; `ORDERS` is `COUNT(*)` and `PRICED_ORDERS` is `COUNT(AMOUNT)`, matching Alteryx's `Count` against `CountNonNull`.
- The `ORDER BY` of `SALES_SUMMARY` spells the NULL placement out (`TOTAL_NET DESC NULLS LAST, REGION ASC NULLS FIRST`): Alteryx puts NULL first ascending and last descending.
- `EXCLUDED_ORDERS` declares no keys (the `edge` golden set holds two byte-identical `ORDER_ID` 103 rows), so its comparison is a row multiset: exact about whether the rows match, while a difference is attributed to a column by nearest-match pairing, which is a heuristic.

## Validation summary

`scripts/validate_build.py wf_0001` runs the build file against each golden set and compares every output of `objective.json` with its golden file, writing the verdicts to `validation.<set>.json` and the workflow-level report to `validation.json`. Read the verdicts, counts and any diff clusters there — this document does not restate them, because a number about data may come only from a script.

The golden sets exercised are the four `manifest.golden_sets` names: `normal`, `period_end`, `empty`, `edge`. Idempotency is checked by running the build twice from the same starting state in two fresh sandboxes and comparing the outputs as row multisets.

Deliberately broken builds live in `samples/wf_0001/broken/` — four broken builds, one realistic translator mistake each (a Filter False side that drops the NULL region, an untruncated `CUSTOMER`, a `NET` rounded from the raw float, a True side that keeps the NULL region) — each with a `broken.json` row naming the diff class the validator reports for it. They exist so the comparison itself stays honest.

## Deployment

The deployable is the one build file, `build.sql`, or the dbt project `workflows/wf_0001/dbt/` that `scripts/export_dbt.py` converted from it (`scripts/validate_dbt.py` ran that project on the same golden data, and `scripts/deploy.py wf_0001 --dbt --database <DB> --schema <SCHEMA>` prints the dbt command for the human's own profile): one of the two is deployed, not both. It is deployed by a human or CI under the deploying role `MIGRATION_CI`, never from an agent session, and only for a workflow whose translate stage is `VALIDATED`. Nothing here has run against a Snowflake account from this repository.

`python scripts/deploy.py wf_0001 --database <DB> --schema <SCHEMA> --src-schema MIG_SRC_WF0001` prints, and by default only prints, the `PUT` of `build.sql` to a stage and the one statement that runs it, `EXECUTE IMMEDIATE FROM @<stage>/build.sql USING (src => '<DB>.<SRC_SCHEMA>', tgt => '<DB>.<SCHEMA>')`, which fills `{{src}}` and `{{tgt}}` with Snowflake's own templating, plus a commented `CREATE TASK` carrying the schedule above. That templated form has not run on any account; `--render` also writes `build.rendered.sql` with the schema names substituted, for an account where it does not.

## Runbook

1. Create the source views: run the DDL `python scripts/gen_source_views.py wf_0001` writes (`<DB>.MIG_SRC_WF0001`, one view per logical source).
2. Run the build: `EXECUTE IMMEDIATE FROM @<stage>/build.sql USING (src => '<DB>.MIG_SRC_WF0001', tgt => '<DB>.<SCHEMA>')` — or the rendered file, if the templated form does not run.
3. The file's first statement, `ALTER SESSION SET TIMEZONE = ..., WEEK_START = ...` (`mappings/global.yaml`'s `session` block), sets the session parameters itself; that `EXECUTE IMMEDIATE FROM` accepts it has not been verified, which is one reason `--render` exists.
4. Check parity locally: `python scripts/compile_check.py wf_0001` then `python scripts/validate_build.py wf_0001`. Exit 0 is a pass, 1 a domain failure, 2 a usage error.
5. Rollback: an `overwrite` output is replaced wholesale and holds no prior state. Restore a target with Snowflake Time Travel (`CREATE OR REPLACE TABLE ... CLONE ... BEFORE (STATEMENT => ...)`) or re-run the Alteryx workflow. There is nothing to undo elsewhere: the build leaves no work table behind.
