Restates `objective.md`, `translation_notes.md`, `validation.json`, `docs/mapping.md`, `intake/mappings.yaml` and `manifest.json`. It adds no claim about behaviour that those artifacts do not support, and it quotes no number about data: every count, diff and verdict lives in `validation*.json`, written by `scripts/validate_build.py`.

**Nothing in this migration has been run on a real Snowflake account or a real Alteryx engine.** "Validated" here means the one build file was executed on the local DuckDB double against golden data produced by `scripts/dev/alteryx_sim.py`, the project's stand-in for the Alteryx engine.

## Purpose

Pairs each region's plan target with its booked actuals, keeps the current year, and totals target, actual and line count per region and period into REGION_ATTAINMENT (replaced on every run) and into ATTAINMENT_HISTORY (merged, so earlier years stay).

## Source mappings

| Alteryx touchpoint | Logical name | Snowflake | Write mode | Confirmed by |
|---|---|---|---|---|
| `C:\data\plan\targets.yxdb` (tool 1) | `TARGETS` | `PLANNING.RAW.TARGETS` | read | owner |
| `C:\data\sales\actuals.yxdb` (tool 2) | `ACTUALS` | `SALES.RAW.ACTUALS` | read | owner |
| `C:\data\out\region_attainment.yxdb` (tool 6) | `REGION_ATTAINMENT` | `ANALYTICS.CURATED.REGION_ATTAINMENT` | overwrite | owner |
| ODBC `PROD_PLAN`, `dbo.ATTAINMENT_HISTORY` (tool 7) | `ATTAINMENT_HISTORY` | `ANALYTICS.CURATED.ATTAINMENT_HISTORY` | merge on `REGION, PERIOD` | owner |

The build file never names any of these tables: a source is read as `{{src}}.<LOGICAL>` and a target written as `{{tgt}}.<LOGICAL>`, and `src` and `tgt` are filled in when it runs. In validation `src` is the golden view schema `MIG_GOLDEN_WF0007_<SET>` and `tgt` is `MIG_WORK`; in production `src` is the view schema `scripts/gen_source_views.py` generates, `MIG_SRC_WF0007`, which maps the same logical names to the tables above.

The ODBC string's user and password are fake placeholders and the parser scrubs them; nothing about the connection reaches a mapping except the alias. One workflow constant, `User.CurrentYear` = `2026` (text), is carried into the filter as a literal.

## Steps

The diagram of these steps against the lines of `build.sql`, and the table of every Alteryx tool with its step and lines, are generated by `scripts/render_mapping.py` into [`docs/mapping.md`](mapping.md); this record does not repeat them.

- **s1 · Pair plan targets with actuals** (tools 1, 2, 3): Reads TARGETS and ACTUALS and inner-joins them on REGION and PERIOD; a target with several actual lines is paired with each, and rows with a NULL key or no partner are dropped.
- **s2 · Keep the current year and total** (tools 4, 5): Keeps the periods whose first four characters equal the workflow constant User.CurrentYear (2026), then sums TARGET and ACTUAL and counts the joined rows per REGION and PERIOD.
- **s3 · Write the attainment summary** (tools 6): Writes REGION_ATTAINMENT, replacing the whole table.
- **s4 · Add to the attainment history** (tools 7): Merges the same rows into ATTAINMENT_HISTORY on REGION and PERIOD: a matched row is overwritten, a new key is inserted and every other row stays.

## Assumptions

Every assumption is listed one per line in `translation_notes.md`; no lint flag is raised, so none is kept. The ones a reader of this document should know about:

- Both outputs total the same rows, so they are built once, in the temporary table `attainment`; `REGION_ATTAINMENT` is a `CREATE OR REPLACE TABLE` over it and `ATTAINMENT_HISTORY` a `MERGE` from it.
- Tool 3 is the J anchor only, an inner join on `=`: a NULL key matches nothing, and a target is paired with each of its actual lines, so its `TARGET` is added once per line, as Alteryx does; a pre-aggregation of the actuals would disagree.
- `User.CurrentYear` is the text constant `'2026'` and tool 4 is `LEFT(PERIOD, 4) = '2026'`, so a malformed period such as `2026-1` is kept, as in Alteryx.
- `Sum` skips NULLs and an all-NULL group is NULL, never 0; `LINES` is `COUNT(*)` because Alteryx's `Count` counts rows; the totals add exact `NUMBER(19,2)` values.
- `ATTAINMENT_HISTORY` is merged on exactly `REGION, PERIOD`: every row the run does not produce stays, prior years included; a NULL update key would match nothing and be inserted, which the inner join never produces here.

## Validation summary

`scripts/validate_build.py wf_0007` runs the build file against each golden set and compares every output of `objective.json` with its golden file, writing the verdicts to `validation.<set>.json` and the workflow-level report to `validation.json`. Read the verdicts, counts and any diff clusters there — this document does not restate them, because a number about data may come only from a script.

The golden sets exercised are the four `manifest.golden_sets` names: `normal`, `period_end`, `empty`, `edge`. Idempotency is checked by running the build twice from the same starting state in two fresh sandboxes and comparing the outputs as row multisets.

Deliberately broken builds live in `samples/wf_0007/broken/` — two broken builds (the year filter not translated, a merge key narrowed to `REGION`) — each with a `broken.json` row naming the diff class the validator reports for it. They exist so the comparison itself stays honest.

## Deployment

The deployable is the one build file, `build.sql`, or the dbt project `workflows/wf_0007/dbt/` that `scripts/export_dbt.py` converted from it (`scripts/validate_dbt.py` ran that project on the same golden data, and `scripts/deploy.py wf_0007 --dbt --database <DB> --schema <SCHEMA>` prints the dbt command for the human's own profile): one of the two is deployed, not both. It is deployed by a human or CI under the deploying role `MIGRATION_CI`, never from an agent session, and only for a workflow whose translate stage is `VALIDATED`. Nothing here has run against a Snowflake account from this repository.

`python scripts/deploy.py wf_0007 --database <DB> --schema <SCHEMA> --src-schema MIG_SRC_WF0007` prints, and by default only prints, the `PUT` of `build.sql` to a stage and the one statement that runs it, `EXECUTE IMMEDIATE FROM @<stage>/build.sql USING (src => '<DB>.<SRC_SCHEMA>', tgt => '<DB>.<SCHEMA>')`, which fills `{{src}}` and `{{tgt}}` with Snowflake's own templating, plus a commented `CREATE TASK` carrying the schedule above. That templated form has not run on any account; `--render` also writes `build.rendered.sql` with the schema names substituted, for an account where it does not.

## Runbook

1. Create the source views: run the DDL `python scripts/gen_source_views.py wf_0007` writes (`<DB>.MIG_SRC_WF0007`, one view per logical source).
2. Run the build: `EXECUTE IMMEDIATE FROM @<stage>/build.sql USING (src => '<DB>.MIG_SRC_WF0007', tgt => '<DB>.<SCHEMA>')` — or the rendered file, if the templated form does not run.
3. The file's first statement, `ALTER SESSION SET TIMEZONE = ..., WEEK_START = ...` (`mappings/global.yaml`'s `session` block), sets the session parameters itself; that `EXECUTE IMMEDIATE FROM` accepts it has not been verified, which is one reason `--render` exists.
4. Check parity locally: `python scripts/compile_check.py wf_0007` then `python scripts/validate_build.py wf_0007`. Exit 0 is a pass, 1 a domain failure, 2 a usage error.
5. Rollback: an `overwrite` output is replaced wholesale and holds no prior state; an `update_insert` output keeps every row the run does not produce and overwrites the ones it matches. Restore a target with Snowflake Time Travel (`CREATE OR REPLACE TABLE ... CLONE ... BEFORE (STATEMENT => ...)`) or re-run the Alteryx workflow. There is nothing to undo elsewhere: the build leaves no work table behind.
