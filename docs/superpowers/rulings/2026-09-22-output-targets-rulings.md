# Coordinator rulings — output targets, phase 1 (2026-09-22 plan)

Every decision the coordinating agent made on its own authority while building
`feat/output-targets`, copied from the build ledger
(`docs/superpowers/build-reports/2026-09-22-output-targets/ledger.md`) in the order they were made.
Format: what — why — cost if wrong. A later ruling that says SUPERSEDES replaces the earlier one it
names. Task numbers refer to `docs/superpowers/plans/2026-09-22-output-targets-phase1.md`, whose
Tasks 3, 4 and 6 carry a note pointing at the rulings that replaced parts of their text. The spec is
`docs/superpowers/specs/2026-09-22-output-targets-design.md`.

Nothing here has run on Snowflake or Alteryx. The Snowpark procedures ran only in the Snowpark Local
Testing Framework; these are engineering decisions about the offline build, to be revisited when the
pipeline meets a real engine.

## Task 1 — the `python` tool

8. Ruling (C1, plan defect): the simulator's Python-tool sandbox is an ACCIDENT GUARD, not a security boundary. Keep the guarded import and restricted builtins, add an AST pre-check that refuses any `__dunder__` attribute or name in the script, and say in `docs/reference/simulator-semantics.md`, `dag-contract.md` and spec §7.1 — in those words — that an allowed library can still reach the filesystem, that the simulator runs only this repository's committed sample scripts, and that it must never be pointed at an untrusted workflow's Python tool. Subprocess or OS isolation is out of scope: it would still not be a security boundary without OS sandboxing, and the honest claim costs nothing — if wrong: a future user runs an untrusted script through test tooling despite the warning.
9. Ruling (C2): dtype detection uses `pandas.api.types` predicates (`is_bool_dtype`, `is_integer_dtype`, `is_float_dtype`, `is_datetime64_any_dtype`) and `pd.isna` uniformly for NULLs, so nullable extension dtypes and `pd.NA` on object columns map correctly; the round-trip test passes a Bool column with NULLs straight through `Alteryx.read` → `Alteryx.write` — if wrong: none.

## Task 3 — Snowpark rules, renderer, `compile_check --target`

12. Ruling: `types_map.alteryx_to_snowpark` mirrors `alteryx_to_snowflake`'s string policy — `String(n)`/`WString(n)` → `StringType(n)`, `V_String`/`V_WString` → unsized `StringType()` — one type policy for both mappings — if wrong: a Snowpark schema is looser than the SQL one; the compare step still judges by family.
13. Ruling: `$$` inside `proc.py` is a DOMAIN failure — `render_snowpark.py` exits 1 (missing files stay 2; any other exception 2) — the fixer can repair content, not a broken invocation — if wrong: none.
14. Ruling (rule set, plan defect; SUPERSEDES the plan's Task 3 code): the AST rules are CONSERVATIVE and structural — (a) `session` may appear only as the receiver of `.table(...)` or `.create_dataframe(...)` inside the one top-level `run`; any other use (binding to another name, passing as an argument, any other attribute, a nested or class-level function taking or referencing it, lambdas, async defs) is `rule:session_scope`; (b) `getattr`, `setattr`, `delattr`, `vars`, `globals`, `locals` are forbidden names; (c) `.table(...)` and `.save_as_table(...)` take exactly one positional literal or C4-parameter f-string and no keywords (`rule:table_names`); (d) `sql_expr`, `call_function`, `call_builtin`, `function`, `call_udf`, `call_table_function`, `table_function` are refused wherever they appear as a name, an attribute or a from-import (`rule:no_raw_sql`); (e) `# tool <id>:` comments are found through `tokenize` COMMENT tokens, never the raw text; (f) exactly one `def run` may exist in the whole module, at top level. The rules stay defence-in-depth (the local double refuses `session.sql` anyway; the policy hook and the Snowflake role are the primary boundary) but must not be evadable by ordinary Python — if wrong: an exotic but legitimate idiom is refused and the translator rewrites it; cheap.
15. Ruling (fix round 2): any dunder attribute access or dunder name anywhere in `proc.py` (other than the already-forbidden `__import__`, which keeps its own message) is refused under the existing rule name `rule:no_io`, mirroring the python-tool sandbox's AST pre-check and keeping the spec's fixed rule-name list — closes `F.__dict__["sql_expr"]` and `F.__getattribute__("sql_expr")` — if wrong: a procedure that needs `__name__`-style introspection is refused, which no C4 procedure needs.

## Task 4 — `validation.py` and `validate_snowpark.py`
