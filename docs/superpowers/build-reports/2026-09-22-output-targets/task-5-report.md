## 3. Brief corrections

### (a) The Python tool's `<Script>` is **not** byte-identical to `tests/test_alteryx_sim_python.py`'s `SCRIPT`

The brief says tool 3's `<Script>` is that `SCRIPT` verbatim. Its last line is
`Alteryx.write(pd.DataFrame(out), 1)`. **That cannot pass the `empty` golden set**, and I proved
it by building the sample with the verbatim script first:

```
wf_0006/empty: tool 4: Summarize reads 'PERIOD', which is not on the incoming stream
wf_0006/empty: tool 4: Summarize reads 'RECOGNIZED', which is not on the incoming stream
...
```

and the produced `golden/intermediates/seg_02/empty/3_1.csv` was a **zero-column** file. The cause
is `pd.DataFrame([])`: with no rows and no column list it has no columns at all. `compare.py`'s
`_schema_problems` would then report `contract columns not in expected` and the `empty` set would
`FAIL` — which contradicts the brief's own "every segment must pass every golden set". Giving the
frame a column list alone is not enough either: an empty object-dtype column maps to `V_WString`,
so `RECOGNIZED`/`DEFERRED` would come back `string` family against the procedure's `FLOAT`.

Smallest correction, applied to the `.yxmd` only:

```python
schedule = pd.DataFrame(out, columns=["CUSTOMER", "PERIOD", "RECOGNIZED", "DEFERRED"])
schedule["RECOGNIZED"] = schedule["RECOGNIZED"].astype("float64")
schedule["DEFERRED"] = schedule["DEFERRED"].astype("float64")
Alteryx.write(schedule, 1)
```

Everything above that line is the brief's `SCRIPT` character for character. The non-empty sets
produce identical output either way (`pd.DataFrame(list-of-dicts, columns=…)` keeps the same
columns, order and dtypes), so this changes nothing but the empty case.

**I did not touch `tests/test_alteryx_sim_python.py`.** It is Task 1's test, its assertions are
about a non-empty frame and still hold, and editing another task's test to match a sample seemed
the wrong direction. The consequence is that the sample's script and that test's `SCRIPT` now
differ in their last three lines. If the controller would rather they were literally identical,
the fix belongs in Task 1's `SCRIPT` (and its `test_shim_runs_the_script_and_types_the_output`
would still pass unchanged). `seg_02/translation_notes.md` records why the explicit schema exists
on the Snowpark side, which is the same reason.

The brief's `proc.py` needed **no** change: it already declares an explicit `StructType`, so an
empty run still writes a four-column `FLOAT`-typed table. I confirmed that against the local
testing framework before writing anything:
`create_dataframe([], schema=…)` → `StructType([... StringType(254) ... DoubleType() ...])`,
`to_pandas()` → `(0, 4)`.

### (b) `seg_01`'s work stream is keyed too

The brief says "keys where unique (`CUSTOMER, PERIOD` for seg_02's stream; `PERIOD` for the
target)" and separately asks the `edge` set for "a byte-identical duplicate row". **Those two are
in tension**: a duplicate that survives the Filter reaches tool 3, which emits one row per input
row, so `(CUSTOMER, PERIOD)` would repeat on `seg_02`'s stream — and `compare.py` reports a
duplicate declared key as a `GOLDEN_DATA` cluster and `FAIL`s.

I resolved it in the data rather than in the contract: the duplicate pair is billed `0.0`, so the
Filter removes both copies before either stream exists. That keeps `seg_02`'s declared keys exactly
as the brief specifies, and it leaves `(CUSTOMER, PERIOD)` unique on `seg_01`'s stream as well — so
I declared it there too, on the brief's own "keys where unique" rule. A reviewer diffing against
the brief will see one key list it does not enumerate; it is the honest one, and it is what lets
the `seg_02` broken variant be reported as a named row (`ACME` / `2026-03`) instead of an
anonymous multiset difference. Both the README and `analysis.md` spell out that the duplicate is
filtered out and why that matters.

## I2 — the NULL `CAP` / NULL `CANCELLED` notes

**I reproduced the reviewer's finding on both engines before changing any prose**, with a mixed
column (one real value, one NULL) — which is the case this workflow actually has:

```
=== simulator (_table_to_pandas) ===
dtypes: {'CUSTOMER': dtype('O'), 'CAP': dtype('float64'), 'CANCELLED': BooleanDtype}
  CAP repr np.float64(nan) -> float() nan | min(120.0, cap) = 120.0
  bool(CANCELLED) RAISES: TypeError boolean value of NA is ambiguous
  pd.isna(CANCELLED) -> True
=== Snowpark local testing (to_pandas) ===
dtypes: {'CUSTOMER': dtype('O'), 'CAP': dtype('float64'), 'CANCELLED': dtype('O')}
  CAP repr np.float64(nan)
  float(CAP) -> nan | min(120.0, cap) = 120.0
  bool(CANCELLED) -> False  <-- SILENT False
  pd.isna(CANCELLED) -> True
```

So my original note was wrong on both halves: a NULL `CAP` raises nowhere and is silently *not* a
cap identically on both sides (parity holds, nothing would ever surface it), and a NULL
