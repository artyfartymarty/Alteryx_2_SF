## Purpose

Pairs each customer with their orders and appends the result to CUSTOMER_ORDER_FACT, flagging each row MATCHED (a customer with an order), NO_ORDERS (a customer with none) or ORPHAN (an order whose customer is unknown).

The build file never names any of these tables: a source is read as `{{src}}.<LOGICAL>` and a target written as `{{tgt}}.<LOGICAL>`, and `src` and `tgt` are filled in when it runs. ## Steps

The diagram of these steps against the lines of `build.sql`, and the table of every Alteryx tool with its step and lines, are generated by `scripts/render_mapping.py` into [`docs/mapping.md`](mapping.md); this record does not repeat them.

- **s1 · Clean the customer list** (tools 1, 2): Reads CUSTOMERS and, for NAME and CITY, replaces NULL with blank, trims the blanks and upper-cases.
- **s2 · Type the orders export** (tools 3, 4): Reads the nightly orders export, where every column arrives as text, and converts ORDER_ID and CUST_ID to whole numbers, AMOUNT to a number and ORDER_DATE to a date; text that cannot be converted becomes NULL.
- **s3 · Match customers to orders and flag the outcome** (tools 5, 6, 7, 8): Joins customers to orders on CUST_ID and flags each outcome: MATCHED for a customer with an order, NO_ORDERS for a customer with none, ORPHAN for an order whose customer is not in the list.
- **s4 · Stack the outcomes and append them** (tools 9, 10): Stacks the three outcomes by column name and appends them to CUSTOMER_ORDER_FACT, which keeps the rows it already holds.
- No effect on the data, tool 11: Browse tool: shows the stacked rows to a person, changes nothing.

## Assumptions

Every assumption is listed one per line in `translation_notes.md`; no lint flag is raised, so none is kept. The ones a reader of this document should know about:

- The two prep groups are the temporary tables `customers_clean` (tools 1 and 2) and `orders_typed` (tools 3 and 4), each read once; the Join's three outputs are built in the one `INSERT INTO` that appends them, with `UNION ALL`. No work table survives the run.
- Tool 2's Data Cleansing options run in the macro's own order: NULL to blank first (trimming a NULL leaves NULL), then trim, then upper-case, so `NAME` and `CITY` are never NULL downstream of it.
- `UPPER` is Snowflake's own Unicode case rules, which are not guaranteed to match Alteryx's for every script; the `edge` golden set exercises Latin Extended and CJK text.
- Every column of the orders export arrives as text; every conversion in tool 4 is a `TRY_` form (Alteryx warns and nulls on text it cannot read), so `'abc'` and the empty string give a NULL `AMOUNT`, and a date that does not exist (`2026-02-30`) or a non-ISO date (`31/12/2026`) gives a NULL `ORDER_DATE`; the date is read with an explicit `YYYY-MM-DD` format.
- Alteryx's integer coercion rounds half away from zero, which `TRY_TO_NUMBER(x, 38, 0)` also does; the sample data is whole numbers, so nothing here proves it.
- Tool 5's Join matches with `=`, so a NULL key matches nothing and the row leaves on L or R; the two anti-join branches use `NOT EXISTS`, where a `NOT IN` would drop every row once the other side held a NULL. Key comparison is exact and case-sensitive.
- Tool 9's Union is by name: every branch is projected into the first branch's column list, with NULL for a field the branch lacks, before the `UNION ALL`.
- The output is appended with an explicit column list (`INSERT INTO {{tgt}}.CUSTOMER_ORDER_FACT (...)`), so columns are matched to the table by name; the golden output is the table's state after the append, the rows it already held included.
- `CUSTOMER_ORDER_FACT` declares no keys, so its comparison is a row multiset.
- Tool 11 is a Browse: it shows rows to a person and changes nothing, so the objective lists it as having no effect and the file has no code for it.

## Validation summary

`scripts/validate_build.py wf_0002` runs the build file against each golden set and compares every output of `objective.json` with its golden file, writing the verdicts to `validation.<set>.json` and the workflow-level report to `validation.json`. Read the verdicts, counts and any diff clusters there — this document does not restate them, because a number about data may come only from a script.

The golden sets exercised are the four `manifest.golden_sets` names: `normal`, `period_end`, `empty`, `edge`. Idempotency is checked by running the build twice from the same starting state in two fresh sandboxes and comparing the outputs as row multisets.

Deliberately broken builds live in `samples/wf_0002/broken/` — three broken builds (a cleansing that does not upper-case, a cleansing that keeps NULL names, a union that drops the Join's left branch) — each with a `broken.json` row naming the diff class the validator reports for it. They exist so the comparison itself stays honest.

## Deployment

The deployable is the one build file, `build.sql`, or the dbt project `workflows/wf_0002/dbt/` that `scripts/export_dbt.py` converted from it (`scripts/validate_dbt.py` ran that project on the same golden data, and `scripts/deploy.py wf_0002 --dbt --database <DB> --schema <SCHEMA>` prints the dbt command for the human's own profile): one of the two is deployed, not both. It is deployed by a human or CI under the deploying role `MIGRATION_CI`, never from an agent session, and only for a workflow whose translate stage is `VALIDATED`. Nothing here has run against a Snowflake account from this repository.

`python scripts/deploy.py wf_0002 --database <DB> --schema <SCHEMA> --src-schema MIG_SRC_WF0002` prints, and by default only prints, the `PUT` of `build.sql` to a stage and the one statement that runs it, `EXECUTE IMMEDIATE FROM @<stage>/build.sql USING (src => '<DB>.<SRC_SCHEMA>', tgt => '<DB>.<SCHEMA>')`, which fills `{{src}}` and `{{tgt}}` with Snowflake's own templating, plus a commented `CREATE TASK` carrying the schedule above. That templated form has not run on any account; `--render` also writes `build.rendered.sql` with the schema names substituted, for an account where it does not.

## Runbook

1. Create the source views: run the DDL `python scripts/gen_source_views.py wf_0002` writes (`<DB>.MIG_SRC_WF0002`, one view per logical source).
2. Run the build: `EXECUTE IMMEDIATE FROM @<stage>/build.sql USING (src => '<DB>.MIG_SRC_WF0002', tgt => '<DB>.<SCHEMA>')` — or the rendered file, if the templated form does not run.
3. The file's first statement, `ALTER SESSION SET TIMEZONE = ..., WEEK_START = ...` (`mappings/global.yaml`'s `session` block), sets the session parameters itself; that `EXECUTE IMMEDIATE FROM` accepts it has not been verified, which is one reason `--render` exists.
4. Check parity locally: `python scripts/compile_check.py wf_0002` then `python scripts/validate_build.py wf_0002`. Exit 0 is a pass, 1 a domain failure, 2 a usage error.
5. Rollback: an `append` output keeps every row it already held, so a bad run's rows have to be deleted from it. Restore a target with Snowflake Time Travel (`CREATE OR REPLACE TABLE ... CLONE ... BEFORE (STATEMENT => ...)`) or re-run the Alteryx workflow. There is nothing to undo elsewhere: the build leaves no work table behind.
