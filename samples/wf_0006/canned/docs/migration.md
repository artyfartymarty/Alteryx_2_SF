## Purpose

Recognises subscription revenue period by period for each customer, carrying unrecognised (deferred) amounts forward until they fit under the customer's cap, and totals what was recognised and deferred per period into REVENUE_BY_PERIOD.

## Source mappings

| Alteryx touchpoint | Logical name | Snowflake | Write mode | Confirmed by |
|---|---|---|---|---|
| `C:\data\billing\subscriptions.yxdb` (tool 1) | `SUBSCRIPTIONS` | `BILLING.RAW.SUBSCRIPTIONS` | read | owner |
| `C:\data\out\revenue_by_period.yxdb` (tool 5) | `REVENUE_BY_PERIOD` | `ANALYTICS.CURATED.REVENUE_BY_PERIOD` | overwrite | owner |

The build file never names any of these tables: a source is read as `session.table(f"{src}.<LOGICAL>")` and a target written as `.save_as_table(f"{tgt}.<LOGICAL>")`, and `src` and `tgt` are filled in when it runs. In validation `src` is the golden view schema `MIG_GOLDEN_WF0006_<SET>` and `tgt` is `MIG_WORK`; in production `src` is the view schema `scripts/gen_source_views.py` generates, `MIG_SRC_WF0006`, which maps the same logical names to the tables above.

## Steps

The diagram of these steps against the lines of `build.py`, and the table of every Alteryx tool with its step and lines, are generated by `scripts/render_mapping.py` into [`docs/mapping.md`](mapping.md); this record does not repeat them.

- **s1 · Keep the billed periods** (tools 1, 2): Reads SUBSCRIPTIONS and keeps the periods whose BILLED is above 0; a period billed exactly 0, or with no BILLED, is dropped.
- **s2 · Build each customer's revenue schedule** (tools 3): For each customer, in CUSTOMER and PERIOD order, carries a deferred balance forward, resets it to 0 when the period is cancelled (before that period's own cap applies), recognises the smaller of billed plus carried and the CAP, defers the rest, and rounds both amounts to 2 decimals.
- **s3 · Total recognised and deferred revenue per period** (tools 4, 5): Sums RECOGNIZED and DEFERRED and counts the schedule rows per PERIOD, and writes REVENUE_BY_PERIOD.

## Assumptions

Every assumption is listed one per line in `translation_notes.md`; no lint flag is raised, so none is kept. The ones a reader of this document should know about:

- The workflow is Python because tool 3's loop carries a deferred balance from one row to the next inside a customer: `min(carried + billed, cap)` does not distribute over a running sum, so no window function expresses it. Tool 3 is the tool that forced `pandas`.
- Tool 2's Filter is `[BILLED] > 0`, strict: a `BILLED` of exactly 0 goes too, and a NULL `BILLED` is dropped as Alteryx's unwired False anchor drops it. It is done on the pandas frame, because the Local Testing Framework cannot filter an empty table.
- Tool 3 sorts by `CUSTOMER, PERIOD` itself, as its script does; a cancellation resets the deferred balance to 0 before that period's own cap applies, and `RECOGNIZED` and `DEFERRED` are rounded with Python's `round`, not Alteryx's `Round`.
- A NULL `CANCELLED` raises (`bool(pd.NA)` does), as the script does, where the framework's `None` would quietly be false; `groupby` drops a NULL `CUSTOMER`, in Alteryx as much as here.
- `to_pandas()` materialises the whole stream, which is safe only because the input is bounded; this is the translation's single scaling assumption.
- A NULL `CAP` that survives the Filter is not guarded: `float(NULL)` is `nan` on both engines and `min(x, nan)` returns `x`, so the cap is silently not applied, identically in Alteryx; it is a data-quality risk in the source, not a translation risk.
- Tool 4 sums a `Double` to a `Double` and counts rows (`CUSTOMERS` is `count(lit(1))`, not a count of customers' values); no sort is applied, the target being keyed on `PERIOD`.
- The output is written with `.write.mode("overwrite").save_as_table(f"{tgt}.REVENUE_BY_PERIOD")`, its column order that of the objective.

## Validation summary

`scripts/validate_build.py wf_0006` runs the build file against each golden set and compares every output of `objective.json` with its golden file, writing the verdicts to `validation.<set>.json` and the workflow-level report to `validation.json`. Read the verdicts, counts and any diff clusters there — this document does not restate them, because a number about data may come only from a script.

The golden sets exercised are the four `manifest.golden_sets` names: `normal`, `period_end`, `empty`, `edge`. Idempotency is checked by running the build twice from the same starting state in two fresh sandboxes and comparing the outputs as row multisets.

Deliberately broken builds live in `samples/wf_0006/broken/` — two broken builds (a cancellation reset ignored, a Summarize that drops `PERIOD`) — each with a `broken.json` row naming the diff class the validator reports for it. They exist so the comparison itself stays honest.

## Deployment

The deployable is the one build file, `build.py`; nothing else in this workflow is deployed. It is deployed by a human or CI under the deploying role `MIGRATION_CI`, never from an agent session, and only for a workflow whose translate stage is `VALIDATED`. Nothing here has run against a Snowflake account from this repository.

`python scripts/deploy.py wf_0006 --database <DB> --schema <SCHEMA> --src-schema MIG_SRC_WF0006` prints, and by default only prints, the one Python stored procedure that wraps the module (`CREATE OR REPLACE PROCEDURE <SCHEMA>.WF0006_BUILD(SRC STRING, TGT STRING)`, `LANGUAGE PYTHON`, `HANDLER = 'main'`) and the `CALL` that runs it. Its `RUNTIME_VERSION` (`mappings/global.yaml`'s `program.snowpark_runtime`) and its `PACKAGES` are the two values to verify against the target account before running the DDL.

## Runbook

1. Create the source views: run the DDL `python scripts/gen_source_views.py wf_0006` writes (`<DB>.MIG_SRC_WF0006`, one view per logical source).
2. Deploy the procedure `python scripts/deploy.py wf_0006 ...` prints, then `CALL <SCHEMA>.WF0006_BUILD('<DB>.MIG_SRC_WF0006', '<DB>.<SCHEMA>')`.
3. The module sets no session parameter: nothing in this workflow depends on `TIMEZONE` or `WEEK_START`.
4. Check parity locally: `python scripts/compile_check.py wf_0006` then `python scripts/validate_build.py wf_0006`. Exit 0 is a pass, 1 a domain failure, 2 a usage error.
5. Rollback: an `overwrite` output is replaced wholesale and holds no prior state. Restore a target with Snowflake Time Travel (`CREATE OR REPLACE TABLE ... CLONE ... BEFORE (STATEMENT => ...)`) or re-run the Alteryx workflow. There is nothing to undo elsewhere: the build leaves no work table behind.

## Open items
