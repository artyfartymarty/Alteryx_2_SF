# wf_0003 — migration record

Restates `objective.md`, `translation_notes.md`, `validation.json`, `docs/mapping.md`, `intake/mappings.yaml` and `manifest.json`. It adds no claim about behaviour that those artifacts do not support, and it quotes no number about data: every count, diff and verdict lives in `validation*.json`, written by `scripts/validate_build.py`.

**Nothing in this migration has been run on a real Snowflake account or a real Alteryx engine.** "Validated" here means the one build file was executed on the local DuckDB double against golden data produced by `scripts/dev/alteryx_sim.py`, the project's stand-in for the Alteryx engine.

## Purpose

Closes a general-ledger period for one region: keeps the latest entry per account and day, runs a balance per account, and loads one row per account and period -- total, closing balance and entry count -- into GL_SUMMARY.

## Source mappings

| Alteryx touchpoint | Logical name | Snowflake | Write mode | Confirmed by |
|---|---|---|---|---|
| ODBC alias `prod_fin`, query on `dbo.GL_LEDGER` (tool 1) | `GL_LEDGER` | `FINANCE.RAW.GL_LEDGER` | read | owner |
| ODBC alias `prod_fin`, table `dbo.GL_SUMMARY` (tool 10) | `GL_SUMMARY` | `ANALYTICS.CURATED.GL_SUMMARY` | merge on `ACCT, PERIOD` | owner |

The build file never names any of these tables: a source is read as `{{src}}.<LOGICAL>` and a target written as `{{tgt}}.<LOGICAL>`, and `src` and `tgt` are filled in when it runs. In validation `src` is the golden view schema `MIG_GOLDEN_WF0003_<SET>` and `tgt` is `MIG_WORK`; in production `src` is the view schema `scripts/gen_source_views.py` generates, `MIG_SRC_WF0003`, which maps the same logical names to the tables above.

The connection string's user id and password were removed by the parser's scrubber and appear nowhere under `workflows/`.

Two workflow constants are resolved at translation time, because Snowflake has no equivalent: `User.Region` = `EMEA` in tool 2's filter and `User.PeriodEnd` = `2026-08-31` in tool 8's formula. Both are recorded under `constants:` in `intake/mappings.yaml`. A run for another region or period needs a re-translation, not a new argument — a real loss of flexibility against the Alteryx workflow, listed under Open items.

## Steps

The diagram of these steps against the lines of `build.sql`, and the table of every Alteryx tool with its step and lines, are generated by `scripts/render_mapping.py` into [`docs/mapping.md`](mapping.md); this record does not repeat them.

- **s1 · Extract the region's ledger entries** (tools 1, 2, 3): Reads GL_LEDGER (the source query keeps only rows whose AMOUNT is not 0), keeps the run's region (the workflow constant User.Region, EMEA) and parses POSTED from dd/mm/yyyy text into a date-time (POSTED_DT).
- **s2 · Keep the latest entry per account and day** (tools 4, 5): Sorts by ACCT, POSTED_DT ascending and ENTRY_ID descending, then keeps the first row for each ACCT and POSTED_DT, which is the one with the largest ENTRY_ID.
- **s3 · Running balance and period-end flag** (tools 6, 7, 8): Adds a running balance (RUN_BAL) per account in that order, numbers the rows (RecordID) and flags the postings made on the period-end date (the constant User.PeriodEnd, 2026-08-31) in PERIOD_END_FLAG.
- **s4 · Close the period and load GL_SUMMARY** (tools 9, 10): Summarizes per ACCT and PERIOD (total AMOUNT, the last RUN_BAL as the closing balance, the entry count, whether any posting is on the period-end date); deletes GL_SUMMARY rows before 2020-01, merges the summary in on ACCT and PERIOD, and then sets LOADED_FLAG to Y where it is still NULL.

## Assumptions

Every assumption is listed one per line in `translation_notes.md`; no lint flag is raised, so none is kept. The ones a reader of this document should know about:

- `User.Region` and `User.PeriodEnd` are workflow constants, resolved here to the literals `'EMEA'` and `'2026-08-31'`; nothing at run time supplies them.
- Tool 1's own query carries `WHERE AMOUNT <> 0`; the file reads the mapped table, so the predicate is written out again (a NULL `AMOUNT` is not `<> 0` either).
- Tool 3 reads `dd/mm/yyyy` text with `TRY_TO_TIMESTAMP_NTZ(POSTED, 'DD/MM/YYYY')`, the warn-and-null form (`31/02/2026` is the row that proves it); `POSTED_DT` is a `TIMESTAMP_NTZ` because an Alteryx DateTime carries midnight.
- Tools 4 and 5 are one `QUALIFY ROW_NUMBER() ... = 1`: the Sort's order is `ENTRY_ID DESC`, so the surviving duplicate of each `ACCT, POSTED_DT` is the one with the largest `ENTRY_ID`, and two NULL `POSTED_DT` rows of one `ACCT` are one key, as `PARTITION BY` treats them.
- Tools 6 and 7 spell the Sort's order out in each window (`ACCT`, `POSTED_DT` ascending NULLS FIRST, `ENTRY_ID` descending NULLS LAST): `RUN_BAL` adds the exact `NUMBER` amounts and casts to `FLOAT` once, which agrees for every amount in the golden sets; a running total long enough to lose a double's precision would not.
- Alteryx's `Last` has no ordered aggregate in either dialect, so `CLOSING_BAL` is `MAX_BY(RUN_BAL, RECORD_ID)`, the same row as long as `RECORD_ID` (a `ROW_NUMBER`) is unique; `ENTRIES` is `COUNT(*)` because Alteryx's `Count` counts rows.
- `HAS_PERIOD_END` is `MAX(IFF(TO_CHAR(POSTED_DT, 'YYYY-MM-DD') = '2026-08-31', 'Y', 'N'))`; a NULL date makes the condition NULL, which takes the else branch, so those rows are `'N'`.
- Output tool 10: the PreSQL (`DELETE ... WHERE PERIOD < '2020-01'`) stands immediately before the `MERGE` and the PostSQL (`UPDATE ... SET LOADED_FLAG = 'Y' WHERE LOADED_FLAG IS NULL`) immediately after it; the merge is on `ACCT, PERIOD` and `LOADED_FLAG` is left alone on a match and arrives NULL on an insert, which the PostSQL then fills.
- A NULL update key matches nothing, so the `edge` set's NULL-`ACCT` group is inserted rather than merged; the golden output is the table's state after all three statements, rows the run never touched included.

## Validation summary

`scripts/validate_build.py wf_0003` runs the build file against each golden set and compares every output of `objective.json` with its golden file, writing the verdicts to `validation.<set>.json` and the workflow-level report to `validation.json`. Read the verdicts, counts and any diff clusters there — this document does not restate them, because a number about data may come only from a script.

The golden sets exercised are the four `manifest.golden_sets` names: `normal`, `period_end`, `empty`, `edge`. Idempotency is checked by running the build twice from the same starting state in two fresh sandboxes and comparing the outputs as row multisets.

Deliberately broken builds live in `samples/wf_0003/broken/` — five broken builds (a month-first date read, a Unique that keeps the lowest `ENTRY_ID`, a PostSQL not translated, a PreSQL not translated, a `Last` translated as `MAX`) — each with a `broken.json` row naming the diff class the validator reports for it. They exist so the comparison itself stays honest.

## Deployment

The deployable is the one build file, `build.sql`, or the dbt project `workflows/wf_0003/dbt/` that `scripts/export_dbt.py` converted from it (`scripts/validate_dbt.py` ran that project on the same golden data, and `scripts/deploy.py wf_0003 --dbt --database <DB> --schema <SCHEMA>` prints the dbt command for the human's own profile): one of the two is deployed, not both. It is deployed by a human or CI under the deploying role `MIGRATION_CI`, never from an agent session, and only for a workflow whose translate stage is `VALIDATED`. Nothing here has run against a Snowflake account from this repository.

`python scripts/deploy.py wf_0003 --database <DB> --schema <SCHEMA> --src-schema MIG_SRC_WF0003` prints, and by default only prints, the `PUT` of `build.sql` to a stage and the one statement that runs it, `EXECUTE IMMEDIATE FROM @<stage>/build.sql USING (src => '<DB>.<SRC_SCHEMA>', tgt => '<DB>.<SCHEMA>')`, which fills `{{src}}` and `{{tgt}}` with Snowflake's own templating, plus a commented `CREATE TASK` carrying the schedule above. That templated form has not run on any account; `--render` also writes `build.rendered.sql` with the schema names substituted, for an account where it does not.

## Runbook

1. Create the source views: run the DDL `python scripts/gen_source_views.py wf_0003` writes (`<DB>.MIG_SRC_WF0003`, one view per logical source).
2. Run the build: `EXECUTE IMMEDIATE FROM @<stage>/build.sql USING (src => '<DB>.MIG_SRC_WF0003', tgt => '<DB>.<SCHEMA>')` — or the rendered file, if the templated form does not run.
3. The file's first statement, `ALTER SESSION SET TIMEZONE = ..., WEEK_START = ...` (`mappings/global.yaml`'s `session` block), sets the session parameters itself; that `EXECUTE IMMEDIATE FROM` accepts it has not been verified, which is one reason `--render` exists.
4. Check parity locally: `python scripts/compile_check.py wf_0003` then `python scripts/validate_build.py wf_0003`. Exit 0 is a pass, 1 a domain failure, 2 a usage error.
5. Rollback: an `update_insert` output keeps every row the run does not produce and overwrites the ones it matches. Restore a target with Snowflake Time Travel (`CREATE OR REPLACE TABLE ... CLONE ... BEFORE (STATEMENT => ...)`) or re-run the Alteryx workflow. There is nothing to undo elsewhere: the build leaves no work table behind.
