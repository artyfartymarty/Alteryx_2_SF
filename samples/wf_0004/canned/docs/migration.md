# wf_0004 — migration record

Restates `objective.md`, `translation_notes.md`, `validation.json`, `docs/mapping.md`, `intake/mappings.yaml` and `manifest.json`. It adds no claim about behaviour that those artifacts do not support, and it quotes no number about data: every count, diff and verdict lives in `validation*.json`, written by `scripts/validate_build.py`.

**Nothing in this migration has been run on a real Snowflake account or a real Alteryx engine.** "Validated" here means the one build file was executed on the local DuckDB double against golden data produced by `scripts/dev/alteryx_sim.py`, the project's stand-in for the Alteryx engine.

## Purpose

Cleans the SKU codes of the warehouse stock list, drops empty stock, and writes two views of it: one row per SKU and family with a quantity column per warehouse (INVENTORY_BY_WH), and the same quantities as one row per SKU and warehouse (INVENTORY_LONG).

## Source mappings

| Alteryx touchpoint | Logical name | Snowflake | Write mode | Confirmed by |
|---|---|---|---|---|
| `C:\data\wh\stock.yxdb` (tool 1) | `STOCK` | `WH.RAW.STOCK` | read | owner |
| `C:\data\out\inventory_by_wh.yxdb` (tool 6) | `INVENTORY_BY_WH` | `ANALYTICS.CURATED.INVENTORY_BY_WH` | overwrite | owner |
| `C:\data\out\inventory_long.yxdb` (tool 7) | `INVENTORY_LONG` | `ANALYTICS.CURATED.INVENTORY_LONG` | overwrite | owner |

The build file never names any of these tables: a source is read as `{{src}}.<LOGICAL>` and a target written as `{{tgt}}.<LOGICAL>`, and `src` and `tgt` are filled in when it runs. In validation `src` is the golden view schema `MIG_GOLDEN_WF0004_<SET>` and `tgt` is `MIG_WORK`; in production `src` is the view schema `scripts/gen_source_views.py` generates, `MIG_SRC_WF0004`, which maps the same logical names to the tables above.

`Supporting_Macros/clean_codes.yxmc` is recorded under `macros:` in `intake/mappings.yaml` as `inline: true`. It is a **shared** macro: it sits beside the workflow rather than inside it, so any other workflow in the estate that uses it is translated against the same sub-DAG, and editing it changes this migration even though `inventory.yxmd` did not change.

## Steps

The diagram of these steps against the lines of `build.sql`, and the table of every Alteryx tool with its step and lines, are generated by `scripts/render_mapping.py` into [`docs/mapping.md`](mapping.md); this record does not repeat them.

- **s1 · Read warehouse stock** (tools 1): Reads the STOCK list: SKU, WAREHOUSE, QTY and NOTE.
- **s2 · Clean SKU codes and drop empty stock** (tools 2): Runs the clean_codes macro with MinQty = 1: normalises each SKU to FAMILY-NUMBER form in upper case (a SKU that does not match is kept as it was) and drops the rows whose QTY is below 1 or NULL.
- **s3 · Split SKU into family and item** (tools 3): Parses SKU into FAMILY (the letters) and ITEM_NO (the digits); a SKU that does not match keeps its row with both NULL.
- **s4 · Pivot quantity by warehouse** (tools 4, 6): Sums QTY per SKU and FAMILY with one column per warehouse (EAST, NORTH, WEST) and writes INVENTORY_BY_WH.
- **s5 · Unpivot to one row per warehouse** (tools 5, 7): Turns the EAST, NORTH and WEST columns back into Name and Value rows per SKU and writes INVENTORY_LONG.

## Assumptions

Every assumption is listed one per line in `translation_notes.md`; no lint flag is raised, so none is kept. The ones a reader of this document should know about:

- The macro's tools are translated in place, in the temporary table `stock_clean`, with its question `MinQty` answered `1` as the workflow passes it, not the macro's own default `0`; stock with `QTY` below 1 or NULL is dropped.
- The macro's RegEx is Replace with `CopyUnmatched` and case-insensitive: `REGEXP_REPLACE` returns a SKU that does not match unchanged, and `UPPER` follows; tool 3's Parse is case-sensitive.
- A SKU the Parse pattern does not match keeps its row with a NULL `FAMILY`; the match is tested with `REGEXP_LIKE` and the NULL written out, because the local DuckDB double returns an empty string where Snowflake's `REGEXP_SUBSTR` returns NULL.
- Snowflake's regex dialect is not Python's, which the simulator uses: `\d` and `\s` are ASCII-only on the local engine and Unicode-aware in the oracle. No golden set contains a non-ASCII digit or a non-breaking space, so the divergence is recorded rather than guarded against.
- `ITEM_NO` and `NOTE` reach neither output, so they are not carried.
- The Cross Tab's header columns are frozen to the tool's `EAST, NORTH, WEST`: a warehouse outside that list has no column and is dropped, in Alteryx as well; a cell with no stock is NULL, not 0, so nothing wraps the `SUM` in `COALESCE`, and the `Double` sum is taken over the exact integers and cast once.
- The Transpose keeps NULL cells (a bare `UNPIVOT` drops them), as a `UNION ALL` of three projections of the pivot just written, read back after its write, with rows within a `SKU` ordered `EAST, NORTH, WEST`; the union is a subquery because the DuckDB double will not `ORDER BY` an expression over a bare `UNION`.
- `INVENTORY_LONG` has `SKU` as its only key field, so `FAMILY` is dropped from the long table.

## Validation summary

`scripts/validate_build.py wf_0004` runs the build file against each golden set and compares every output of `objective.json` with its golden file, writing the verdicts to `validation.<set>.json` and the workflow-level report to `validation.json`. Read the verdicts, counts and any diff clusters there — this document does not restate them, because a number about data may come only from a script.

The golden sets exercised are the four `manifest.golden_sets` names: `normal`, `period_end`, `empty`, `edge`. Idempotency is checked by running the build twice from the same starting state in two fresh sandboxes and comparing the outputs as row multisets.

Deliberately broken builds live in `samples/wf_0004/broken/` — five broken builds (a macro Filter dropped, the macro's question default used, a macro RegEx that nulls unmatched SKUs, a Cross Tab that fills missing cells with zero, a Transpose that drops NULL cells) — each with a `broken.json` row naming the diff class the validator reports for it. They exist so the comparison itself stays honest.

## Deployment

The deployable is the one build file, `build.sql`, or the dbt project `workflows/wf_0004/dbt/` that `scripts/export_dbt.py` converted from it (`scripts/validate_dbt.py` ran that project on the same golden data, and `scripts/deploy.py wf_0004 --dbt --database <DB> --schema <SCHEMA>` prints the dbt command for the human's own profile): one of the two is deployed, not both. It is deployed by a human or CI under the deploying role `MIGRATION_CI`, never from an agent session, and only for a workflow whose translate stage is `VALIDATED`. Nothing here has run against a Snowflake account from this repository.

`python scripts/deploy.py wf_0004 --database <DB> --schema <SCHEMA> --src-schema MIG_SRC_WF0004` prints, and by default only prints, the `PUT` of `build.sql` to a stage and the one statement that runs it, `EXECUTE IMMEDIATE FROM @<stage>/build.sql USING (src => '<DB>.<SRC_SCHEMA>', tgt => '<DB>.<SCHEMA>')`, which fills `{{src}}` and `{{tgt}}` with Snowflake's own templating, plus a commented `CREATE TASK` carrying the schedule above. That templated form has not run on any account; `--render` also writes `build.rendered.sql` with the schema names substituted, for an account where it does not.

## Runbook

1. Create the source views: run the DDL `python scripts/gen_source_views.py wf_0004` writes (`<DB>.MIG_SRC_WF0004`, one view per logical source).
2. Run the build: `EXECUTE IMMEDIATE FROM @<stage>/build.sql USING (src => '<DB>.MIG_SRC_WF0004', tgt => '<DB>.<SCHEMA>')` — or the rendered file, if the templated form does not run.
3. The file's first statement, `ALTER SESSION SET TIMEZONE = ..., WEEK_START = ...` (`mappings/global.yaml`'s `session` block), sets the session parameters itself; that `EXECUTE IMMEDIATE FROM` accepts it has not been verified, which is one reason `--render` exists.
4. Check parity locally: `python scripts/compile_check.py wf_0004` then `python scripts/validate_build.py wf_0004`. Exit 0 is a pass, 1 a domain failure, 2 a usage error.
5. Rollback: an `overwrite` output is replaced wholesale and holds no prior state. Restore a target with Snowflake Time Travel (`CREATE OR REPLACE TABLE ... CLONE ... BEFORE (STATEMENT => ...)`) or re-run the Alteryx workflow. There is nothing to undo elsewhere: the build leaves no work table behind.
